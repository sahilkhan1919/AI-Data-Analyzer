## 3. Existing Data-Storage Behavior

- **In-memory only**: `DATASETS = {}` — a module-level dictionary
- Datasets are lost on every process restart
- Multiple Gunicorn workers do **not** share this dictionary
- No persistence, no TTL, no cleanup mechanism
- Dataset IDs are UUIDs generated by `uuid.uuid4()`

---

## 4. Existing Upload Handling

- Reads `request.files["file"]`
- Extension-based detection (`.csv` → pandas CSV, `.xlsx` → pandas Excel)
- No file-size limit configured (no `MAX_CONTENT_LENGTH`)
- Used `file.filename` directly (not sanitized)
- No UUID validation on dataset IDs

---

## 5. Existing Error-Handling Behavior

- Simple `try/except Exception as e: return jsonify({"error": str(e)}), 500`
- All errors returned as 500 regardless of actual cause
- Error messages could expose Python exception details (tracebacks via `str(e)`)
- No centralized error handlers
- No structured error format

---

## 6. Existing Security Weaknesses

| Issue | Risk |
|-------|------|
| CORS `origins="*"` | Any origin can call the API |
| No `MAX_CONTENT_LENGTH` | Denial-of-service via large uploads |
| `str(e)` in error responses | Python internals leaked to clients |
| Unsanitized filename used in paths | Path traversal risk |
| No UUID validation before dict lookup | Invalid dataset IDs cause `KeyError` |
| Debug mode always on (`debug=True`) | Stack traces in production |
| No input validation on any endpoint | Unhandled exceptions from bad params |
